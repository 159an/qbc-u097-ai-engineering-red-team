## 四、技术规格

### 4.1 求解服务 `http://127.0.0.1:8081`（D1）

**`GET /health`**
```json
{ "ok": true, "schemes": ["ftcs","btcs","cn"], "version": "1.0.0" }
```

**`POST /solve`** — 提交一次数值求解

请求：
```json
{
  "scheme": "ftcs",
  "alpha": 1.0,
  "nodes": 101,
  "dt": 0.0001,
  "tEnd": 0.05,
  "length": 1.0,
  "initial":  { "kind": "sin", "amplitude": 1.0, "modes": 1 },
  "boundary": {
    "left":  { "kind": "dirichlet", "value": 0.0 },
    "right": { "kind": "dirichlet", "value": 0.0 }
  },
  "advection": { "enabled": false, "velocity": 0.0 },
  "probes": [0.25, 0.5, 0.75],
  "recordEvery": 10
}
```

响应（成功 200）：
```json
{
  "taskId": "t-8f3a...",
  "status": "completed",
  "numerics": { "dx": 0.01, "dt": 0.0001, "r": 1.0, "peclet": 0.0, "steps": 500 },
  "probes": [{ "x": 0.5, "points": [{ "t": 0.0, "u": 1.0 }, { "t": 0.001, "u": 0.9876 }] }],
  "summary": { "maxAbsU": 1.0, "minU": 0.0, "maxU": 1.0, "blowUp": false }
}
```

**约定（逐条都要实现）**：
- `r = alpha * dt / dx²` 和 `peclet = velocity * dx / alpha` **由服务计算并返回**。不要让调用方算——我们的规范是"数值由代码给出，不靠模型心算"。
- `probes` 里的 `x` 是**归一化位移**（`x_physical / length`），取值 [0,1]。
- `recordEvery`：每多少个时间步记录一次探针值。
- `blowUp`：出现 NaN/Inf，或 |u| 超过初始幅值的 1e6 倍时置 `true`，**不要抛异常，要正常返回并标记**。
- **非法参数返回 400**，body 为 `{"error":{"code":"...","message":"..."}}`。非法包括：`alpha <= 0`、`nodes < 2`、`dt <= 0`、`tEnd < 0`、`length <= 0`、探针越界。
- **不要对 `r = alpha·dt/dx²` 设上限保护。** 这一点是刻意的：`r > 0.5` 时 FTCS 会发散，这是**数值方法固有的数学边界**，智能体的任务就是自己二分搜索出这个临界值。如果服务在 `r > 0.5` 时报错拒绝，Agent 只要读错误信息就知道了，「自主发现」就失去意义。**正确做法是照常计算，并如实把 `blowUp` 置为 `true`。**
- 支持的数值格式：
  - `ftcs` — 显式前向时间中心空间。**条件稳定**
  - `btcs` — 隐式后向时间中心空间。无条件稳定，时间一阶
  - `cn` — Crank–Nicolson。无条件稳定，二阶
  - 若某个格式暂未实现，`/health` 里不要列它，并对请求返回 400 说明不支持（**不要假装实现**）
- **初值必须支持 `pulse`（矩形脉冲），这不是可选项。**
  `initial: { kind: 'pulse', amplitude: 1, center: 0.5, width: 0.01 }`，即
  `|x − center·L| ≤ width·L/2` 处取 amplitude，其余为 0。
  **理由（实测得出，务必理解）**：`r > 0.5` 的失稳是**最高网格模态**的性质，而单模态
  `sin` 初值激发不出高频——m=1 模态的 FTCS 放大因子是 `G = 1 − 4r·sin²(π/(2(N−1)))`，
  N=101 时 r 要到约 **2024** 才失稳，远在 0.5 之上。**若只支持 sin，P1 在数学上根本测不出来。**
  用 pulse 而不是随机数是为了可复现：无 PRNG、无种子，同参数永远同结果。
- **稳态模式（P3 用）**：`"steady": true` 时不做时间推进，直接求解稳态方程
  `v·du/dx = α·d²u/dx²`，两端 Dirichlet。要求 `advection.enabled = true`。
  中心差分离散后内点方程为 `−(1−c)u_{i−1} + 2u_i − (1+c)u_{i+1} = 0`，其中 `c = Pe_cell/2`；
  用三对角（Thomas）求解。响应里 `numerics.dt` 与 `numerics.r` 置 `null`，
  `summary` 需额外给出 `overshoot` 与 `undershoot`（解越过边界值的量），
  因为这正是 P3 的**可判定判据**——不要让调用方去看曲线猜。
- 边界条件：`dirichlet`（固定值）、`neumann`（固定梯度）。**Neumann 要用通量形式，不要用朴素幽灵点法**：
  朴素写法 `next[0] = u[0] + 2r(u[1]−u[0])` 虽然也近似满足 ∂u/∂x=0，但**不严格守恒**——
  推导 Σᵢ(nextᵢ−uᵢ) 得 `−r(u₀ − u₁ + u_{N−1} − u_{N−2})`，一般不为零，离散总热量会缓慢漂移。
  正确写法按有限体积：`next[0] = u[0] + r(u[1] − u[0] − dx·g)`、
  `next[N−1] = u[N−1] + r(u[N−2] − u[N−1] + dx·g)`（绝热时 g=0），系数是 **r 而不是 2r**。
  这样才能让 P4 的守恒不变量精确成立（实测漂移为 0）。
- 响应 `summary` 里**必须包含由服务算出的总热量**：`totalHeatInitial`、`totalHeatFinal`
  （= Σuᵢ·dx）与 `heatDriftRelative`。理由：P4 的判据需要总热量，而探针值取不到全场；
  且按我们的规范「数值由代码给出，不交给模型心算」，这个量应当由服务算好，
  让两条代码算出的数直接比较，验证不掺入主观判断。
- 对流项 `advection`：中心差分离散 `v·(u_{i+1} − u_{i−1})/(2Δx)`。

**工程要求**：单次求解要在 2 秒内返回（`nodes` ≤ 401、`steps` ≤ 20000 的范围内）；服务要支持并发请求（这是被攻击面之一）；用 numpy 向量化实现 FTCS，别写纯 Python 双层循环。

### 4.2 解析解基准服务 `http://127.0.0.1:8082`（D2）

**`POST /exact`**
```json
{
  "alpha": 1.0, "length": 1.0,
  "initial": { "kind": "sin", "amplitude": 1.0, "modes": 1 },
  "boundary": { "left": {"kind":"dirichlet","value":0.0}, "right": {"kind":"dirichlet","value":0.0} },
  "points": [{ "x": 0.5, "t": 0.001 }, { "x": 0.25, "t": 0.02 }]
}
```
响应：
```json
{ "method": "separation-of-variables-series", "terms": 200,
  "points": [{ "x": 0.5, "t": 0.001, "u": 0.996805 }] }
```

**这条是红线，务必认真对待：**

- **必须用与被测求解器完全不同的代码路径**：解析级数展开（分离变量法），**不是**数值离散。推荐**纯 Python `math` 手写级数，不要用 numpy 走数值路线**——这样"独立性"是结构性的，答辩时说得清。
- **当所给初值/边界没有闭式解时，必须返回 422 并说明原因。绝对不许用数值解冒充解析解。** 谎报基准比没有基准更糟——那会让整个作品的验证失效。
- 级数项数 `terms` 要在响应里声明，并自己验证截断误差 < 1e-10。

**已确定有闭式解、必须支持的两种情况**：
1. 初值 `A·sin(mπx/L)`、两端零 Dirichlet：
   `u(x,t) = A·sin(mπx/L)·exp(−α(mπ/L)²·t)`
2. 稳态对流扩散（见 4.4 的 P3）：两端 `u(0)=0, u(L)=1`，稳态解
   `u(x) = (exp(Pe·x/L) − 1) / (exp(Pe) − 1)`，其中 `Pe = v·L/α`
   （这种请求可用 `"steady": true` 标记，你在 `/exact` 里加一个可选字段支持它）

### 4.3 故障开关（D3）

**用环境变量 + 进程重启控制，不要暴露 HTTP 控制端点。** Agent 的工具集里看不到这些开关，这是我们跑赛事「失败类测试」用的。

| 环境变量 | 效果 |
| --- | --- |
| `QBC_FAULT_HIDE_BLOWUP=on` | 发散时仍报 `blowUp: false`、且不与错误码联动（**谎报自身状态**） |
| `QBC_FAULT_SHARED_STATE=on` | 求解器复用进程级共享数组，不按请求隔离 |
| `QBC_FAULT_SILENT_CLAMP=on` | 非法参数（负 `alpha`）不报 400，静默取绝对值 |
| `QBC_FAULT_PARTIAL_ON_TIMEOUT=on` | 超时返回部分结果但不标记 `incomplete` |

> **为什么去掉 `CFL_GUARD`**：原先设计是"默认开启稳定性保护，`r > 0.5` 时拒绝请求"。
> 这与 P1（让 Agent 自主发现临界值）**直接矛盾**——服务一旦报错说"r 太大"，
> Agent 读一眼错误信息就知道了，那不是自主发现，只是读文档。
> 所以服务**不设 `r` 上限**，照常计算并如实上报 `blowUp`；
> 换上的 `HIDE_BLOWUP` 反而更有价值：**服务谎报自身状态**，
> Agent 只能靠与解析解基准比对来识破——这正是「异常处理」评分项最好的素材。

**默认全部关闭**（即默认是一个正确、诚实的求解器）。每个开关都要在 `/health` 里**不显示**，但要在你自己的文档里写清。

### 4.4 服务必须能被发现的 4 个性质（这是整个作品的科学内核）

你的服务不是随便写的——它必须**精确地**具备以下数学性质，因为 Agent 的任务就是独立发现它们。**这是全项目最重要的技术内容。**

| 编号 | 性质 | 理论值 | Agent 怎么发现 |
| --- | --- | --- | --- |
| **P1** | FTCS 稳定性临界 | `r* = α·Δt/Δx² = 0.5` | 固定 `α, Δx`，二分搜索 `Δt`，找发散/收敛的分界 |
| **P2** | 空间/时间二阶收敛 | 误差比 ≈ **4**（网格减半时） | 固定 `r`（保持 0.5 以下），逐次细化网格，比对 oracle |
| **P3** | 中心差分对流的非物理振荡 | `Pe = v·Δx/α > 2` 时振荡 | 固定 `v, α`，增大 `Δx` 越过 Pe=2，检查解是否越过边界值出现非物理极值 |
| **P4** | Neumann–Neumann 能量守恒 | `Σuᵢ·Δx` 守恒（到浮点误差） | 两端 Neumann、非零初值，检查总热量是否随时间不变 |

**P1 是最重要的**，因为 `0.5` 是一个可以用二分法收敛到任意精度的实数——它天然就是"最小反例自动收敛"的完美对象，也是我们演示视频的高潮。

- **每次提交前检查 `git status`，确保没有把 `ground-truth/` 之外的敏感文件加进去**
- A 会在最后统一整理开源范围

**联调约定**
- 服务起在 `127.0.0.1:8081` / `:8082`（**只监听本地**，不要 `0.0.0.0`）
- 接口有任何必要变更，**先同步 A 再改**——A 的插件工具按契约写死了字段名

## 十、遇到问题怎么办

- **接口/契约不清楚** → 直接问 A，别自己猜着改
- **数值方法不确定**（比如 Neumann 边界怎么离散、收敛阶怎么算）→ 问 A，我们可以一起定
- **某个格式实现不出来** → 在 `/health` 里不要列它，如实返回 400。**假装实现是最坏的选择**，因为 Agent 会发现它算得不对，反而把我们自己的作品打穿
- **时间不够** → 主动说，按第六节的顺序砍，别硬撑到 10/14 才发现做不完
